# SASL / Keycloak Skill

Reference for Nefarious's local SASL path (direct Keycloak auth via libkc) and its three-tier dispatch. For the P10 SASL relay wire format see the `p10-protocol` skill; for libkc's event integration and the ircd/kc boundary see the `nefarious-codebase` skill.

## Local SASL (Keycloak Direct)

- `ircd/sasl_auth.c` / `include/sasl_auth.h` — local SASL PLAIN via a Keycloak ROPC grant through libkc.
- Three-tier dispatch in `m_authenticate.c`: **local Keycloak → IAuth → P10 relay**.
- `sasl_local_available()` checks `sasl_local_initialized && FEAT_SASL_LOCAL && kc_sasl_healthy` (always 0 in a build without libkc).
- Health tracking via `sasl_health_cb` — a health change (`sasl_mark_unhealthy()` / `sasl_mark_healthy()`) tells clients the difference in what `CAP LS` says of `sasl` (`sasl_told_snapshot()` before the flag flips, `sasl_tell_change()` after, `ircd/sasl_mechs.c`): `CAP NEW` with a fallback's value (services' list or `SASL_DEFAULT_MECHANISMS` while a server matching `SASL_SERVER` is linked, or IAuth's list) or nothing when equal; `CAP DEL` only when no fallback offers `sasl`. The services server linking (`sasl_mechanisms_server_linked()`, end of burst) or leaving (`sasl_mechanisms_server_gone()`) is told the same way (`cap_sasl_offered()` with `SASL_SERVER_LINKING` / `SASL_SERVER_LEAVING` for the "before"), except while IAuth handles SASL.
- libkc HTTP detail (libkc is vendored in `ircd/kc/`): `CURLOPT_POSTFIELDSIZE` must be set **before** `CURLOPT_COPYPOSTFIELDS` (per curl docs); `kc_http.c` does so. `kc_http_sync.c` uses plain `CURLOPT_POSTFIELDS` (no copy), where the order does not matter.

## Mechanism Support

The local handlers all live in `sasl_auth.c` and are dispatched by `sasl_start()`. Which mechanisms get *advertised* is gated by `FEAT_SASL_LOCAL_MECHANISMS` (default `"PLAIN,OAUTHBEARER"`), so the off-by-default ones must be added there to appear in CAP.

- **PLAIN** — SASL_LOCAL, iauthd-ts, and services (X3) relay. Advertised by default.
- **OAUTHBEARER** — SASL_LOCAL only. Advertised by default.
- **EXTERNAL** — SASL_LOCAL has a real handler (`sasl_handle_external`): matches the TLS client-cert fingerprint `cli_sslclifp()` against Keycloak's `x509_fingerprints` attribute via `kc_user_search`. Also available via the services (X3) relay. iauthd-ts does NOT support it (PLAIN only). Off by default.
- **SCRAM-SHA-256** — fully implemented in SASL_LOCAL (`sasl_scram_*`, HMAC-SHA256 ClientProof verification against Keycloak-stored creds, read with `kc_user_get`). Off by default.
- **ECDSA-NIST256P-CHALLENGE** — fully implemented in SASL_LOCAL (`sasl_handle_ecdsa`, 32-byte challenge + `EVP_DigestVerify`; public key read with `kc_user_get`). Off by default.

## REGISTER (draft/account-registration) is a login

- A successful REGISTER (e-mail verification off) logs the client in through the SASL login's own completion: `sasl_register_login()` -> `sasl_login_apply(..., LOGIN_BY_REGISTER)`. Same identity, 900, hidden host, metadata/modes, account-notify, AC, bouncer aliases; REGISTER SUCCESS replaces 903 and comes before the 900 (the spec's example). It takes and releases no registration hold and leaves an in-flight SASL exchange alone (REGISTER and SASL may overlap); the registration check goes to the event loop (`auth_set_account_later()`). Do not add steps to one path only.
- The new account's Keycloak id comes from the create's 201 `Location` header (`kc_http` keeps the final block's single Location, never a trailer's, in `kc_http_response.location`; `kc_url_location_user_id()` accepts only `<users URL the create went to>/<UUID>`; `kc_user_create_full()`'s `kc_create_cb` hands it over). No Location: one `kc_user_get` by name, REGISTER SUCCESS after it; a failed lookup, another user's record or a non-UUID id logs in without an id. An id from Keycloak is used (URL path, log, login) only once it is a UUID; raw wire values are logged through `kc_url_log_safe()`. The id counts as Keycloak-confirmed (`id_live`). Verification on: no login, the mail goes to that id.
- A REGISTER answer that finds a SASL login finished meanwhile keeps that login: same account -> REGISTER SUCCESS alone; registered and logged in to another -> `WARN REGISTER ALREADY_AUTHENTICATED <account>` ("log in to it on a new connection": switching is refused, #223); before registration the later answer replaces the login. A bouncer revive before the answer moves `cli_regcookie` onto the ghost, so the answer reaches it.
- REGISTER's names: nick characters, minus every character the ircd's casemapping folds together with another that is not its letter case (`reg_folding_chars()`, read from `ToLower()`; rfc1459: `[\]^` and `{|}~`), refused before Keycloak is asked -- Keycloak's existence check folds letter case only. Why: the ircd compares account names under its casemapping (sessions, history, metadata keys), Keycloak's "name taken?" folds letter case only, so `name{` beside `name[` would be one account to the ircd. A create Keycloak refuses is answered by `kc_classify_create_error()` (an error's `field` decides when present, else its message with password before email before username; across several errors username, email, password): 409 username/email -> ACCOUNT_EXISTS / UNACCEPTABLE_EMAIL; 400 username/email/password-or-credential -> BAD_ACCOUNT_NAME / INVALID_EMAIL / WEAK_PASSWORD, any other 400 -> INVALID_PARAMS; TEMPORARILY_UNAVAILABLE only for 5xx, timeouts, token trouble. `doc/readme.features` (REGISTER_VERIFY_EMAIL) lists them.

## Re-authentication: SASL 3.1 vs 3.2, and SASL_REAUTH

- **SASL 3.1 vs 3.2 (the CAP version decides).** Re-authentication is SASL 3.2's, which is SASL on CAP 302. A connection whose highest `CAP LS` version is below 302 (`cli_capab_version()`; `cap_version_after_ls()` never lowers it, so `CAP LS 302` then `CAP LS` stays 302 -- an explicitly requested `cap-notify` does not make a client 302) is a 3.1 client: after registration every AUTHENTICATE line -- any mechanism, data, `*`, no parameter, even without the sasl cap, logged in or not -- gets 462 ERR_ALREADYREGISTRED (stock master's answer: its command table sends a registered client's AUTHENTICATE to `m_registered()`), first thing in `m_authenticate()`, reaching no tier; before registration, once it has a login (903, or `IsAccount()`: WEBIRC, login-on-connect, REGISTER) any further AUTHENTICATE gets `FAIL AUTHENTICATE ALREADY_AUTHENTICATED` + 907, OAUTHBEARER included. A failed (904) or aborted (906) exchange completes nothing: retry allowed. Everything below is the 3.2 (CAP LS 302) client's.
- **`SASL_REAUTH` (owner's rulings 2026-11-15): `any` (DEFAULT), `same`, `refresh`.** Deploy note: the default lets a logged-in client switch accounts on one connection; a network whose policy is one account per connection sets `refresh`. A string feature with a fixed set of values (`F_SC`, `ircd_features.c`: another value is a bad feature value, 494 / CONFIG error, and the previous value stays even across a rehash); not advertised. `sasl_reauth_mode()` reads it at the start (`m_authenticate()`: `sasl_reauth_mechanism_allowed()`) and again at the completion (`sasl_reauth_refused()`): a REHASH between, the completion decides; `FLAG_SASLREAUTHTOKEN` remembers that the re-authentication began with OAUTHBEARER (cleared by `EndSASLExchange()`).
- For a registered, **logged-in** 3.2 client (`sasl_logged_in()`: the ircd has applied an account -- registered with one, or past registration's auth stage: a login waiting for burst convergence, a revived/attached connection): `refresh` = only OAUTHBEARER starts (else 907) and only its own account (else 907); `same` = any mechanism, own account only (else 907); `any` = any mechanism, own account a refresh, another account an **account change** unless `sasl_switch_allowed()` says no (a bouncer session's connection -- `sasl_session_member()`: `bounce_client_in_session()`, which walks EVERY session (an alias, a primary slot, a roster entry) whatever the client's account, or a held ghost; never `bounce_get_session()`, which looks up through the client's CURRENT account and misses a primary services renamed; a client registration has not applied yet; a name only the casemapping tells apart; no `EXTENDED_ACCOUNTS`): 907. Every setting: the same name under another Keycloak id (the session's id for a primary/alias, else the client's) is 904 (user 2026-10-23: that connection is the previous user's) -- only where the login carries an id (the local Keycloak tier; a services relay carries none, and the same name there is a refresh); a failed re-authentication leaves the login untouched. A side with no id leaves the name to decide (same name: refresh; an id-less login adopts the token's id as before). Refusals: `FAIL AUTHENTICATE ALREADY_AUTHENTICATED` (no context, the reason in its text; standard-replies only) + the numeric; another account and another id also get a NOTICE log line and a rate-limited SNO_UNAUTH notice (two rates).
- **The account change** (`any`) is `sasl_login_apply()`'s `switching`: a new login in every way (record, Keycloak id and its live mark, 900/903) but step 5 (no hidden-host setup) and step 7's 'M': account-notify (session form: channels + the user's own connections), `AC <user> M <account> <ts> [<id>]` -- the ts slot ALWAYS there, "0" for a local Keycloak login (`sasl_broadcast_account()`: a stock server keeps the old account's ts on an M without one; master and the fork store atoi(), X3 binds `account:0` without a ts check) -- `metadata_load_account()` (also pulls the account's rows and read markers from fork peers), `hide_hostmask()` when hidden, `metadata_mode_sync_rederive()` (every mode-synced flag from the new account's row, else the class default -- nothing kept from the old account, +b above all; no hold-on planner, no session joined or made) and the attached persistence profile cleared, `member_ban_cache_clear()` (account bans), a NOTICE log line; the authusers count is unchanged (already counted). Every local account change clears the member ban cache (step 7, `ms_account()` R/M/U and the legacy form for a local user, the webhook deauth, a +r by mode); a remote user's memberships cache nothing. A receiver told a switch (`M` from the user's own server) for a connection IT holds as a session member applies it and logs + SNO_NETWORK-notices it (rate-limited), no repair. **Deploy: keep `refresh`/`same` until every fork server runs this build** -- an older fork server reads every M as a rename and spreads the inherited presence window (PN).
- **Rename vs switch on the wire:** the same `AC <user> M` line. X3 sends M only from `irc_rename()` (nickserv RENAME, from X3's own server, no ts); the fork sends it only from `sasl_broadcast_account()` for its own client; every relay keeps the source (fork and master `ms_account()` relay with `sptr`). So `ms_account()` reads an M from the user's own server (`cli_user()->server`) as a switch, from any other as a rename: `presence_anchor_move(..., carry)` -- a rename carries the open strict-presence interval's start, a switch opens the new account at the change (else the new account reads history from before it logged in). An older fork server treats every M as a rename.
- Before registration (nothing on the network yet) a 3.2 client with a login: `refresh` = only OAUTHBEARER may go again; `same`/`any` = any mechanism; either way as anyone. Who may start again is the orchestrator's choice, not an owner ruling: kept to `sasl_restart_mechanism_allowed()`. **The login it holds stands until the new exchange succeeds** (owner's ruling 2026-11-15, uniform with registered clients; it used to be cleared at the start, 8d1fd129): the start sets `FLAG_SASLREAUTH` as for a re-authentication (`IsSASLExchangeDone()` false), the flag, `FLAG_REGLOGIN`, the identity (`sasl_identity_set()`) or a LOC/WEBIRC account stay, every non-success end (908/904, 905, 906, timeout, agent or IAuth gone) only ends the exchange, a success replaces the identity as a whole (step 1 / IAuth Z), and registration applies whichever stands (`auth_complete_sasl()`, which aborts a still-running exchange with 906). REGISTER stays refused throughout (the flag is never dropped). A 3.1 client gets 907. A registered 3.2 client with no account: a first login, unchanged. REGISTER logins: unchanged.
- Where: `sasl_login_apply()` step 0, which every tier's completion passes (5 local mechanisms, both OAUTHBEARER strategies, services D S); a services `L` and an IAuth `L` run the same `sasl_reauth_refused()` at the L, before anything is named for the exchange (`cli_saslnamed`). A REGISTER login (`LOGIN_BY_REGISTER`) skips step 0: REGISTER answers an account holder itself. A client logged in by REGISTER SUCCESS is logged in like any other. Do not add a completion path that skips it. (IAuth serves no registered client: its "904 service unavailable" after registration is separate and unchanged.)
- The login stays whole while a re-authentication runs: its SASL-complete flag, its `FLAG_REGLOGIN` and its record (`cli_sasl*`); `FLAG_SASLREAUTH` marks the exchange as not completed (`IsSASLExchangeDone()`, as for a REGISTER login mid-exchange) so abort/timeout/agent-split see it in flight.
- Same account = `ircd_strcmp()`-equal AND equal but for ASCII letter case (`sasl_same_name()`, `sasl_same_account()`): names only the casemapping folds (`a[b`/`a{b`) are different accounts, refused whatever the ids say, and never an account change (an M naming one is dropped by every server as no change).
- A refresh keeps its login's record (step 1): the client's own account spelling (also in the 900), its timestamp unless the login brings one (X3's stamp), its Keycloak id (the token's only when it had none), id-live kept for a locally checked token and set when Keycloak confirms the same id now. Step 5 (hidden host) is skipped on a refresh. No AC line.
- Every end of an exchange goes through `EndSASLExchange()` (cookie, start, named account, `FLAG_SASLREAUTH`, `FLAG_SASLREAUTHTOKEN`): never drop a cookie by hand. A 908 (the tier does not offer the mechanism: services `M`, IAuth `l`) ends the exchange at once with its 904. A bouncer hold ends an exchange in flight as `exit_client()` does (`bounce_hold_session()`: `sasl_session_free()` + `abort_sasl()`). A cookie with no local session is another tier's exchange: Path 1 starts no local exchange over it. IAuth `L`/`Z`/`f` with no cookie are dropped; iauthd-ts drops a check's answer when its exchange was aborted or replaced (a per-client serial: the IAuth wire has no cookie).
- A services `AC M` (X3 handle RENAME) can still change a registered user's account, bouncer session members included -- not through SASL. X3 rebinds on an M (x3 #62) but keeps channel access/ops it gave under the old handle, and a vhost from the old account stays until x3 #73.

## SASL_MAX_FAILURES (owner's rulings, 2026-11-15)

- Default 5, 0 = no limit. `con_sasl_failures` counts a connection's failed exchanges; `sasl_failure_count()` (sasl_auth.c) is the one counter, called where an exchange ends without a login through the client: `sasl_fail_reply()` (the local tier's client-caused 904s: bad credentials by the grant's result FORBIDDEN/NOT_FOUND/UNVERIFIED, the negative cache, malformed data, refused tokens, SCRAM/ECDSA proof and lookup "no such user"), a refused token's end after an error challenge (unless `session->fail_unavailable`: introspection could not be asked), 905 on an exchange in flight (m_authenticate.c and sasl_continue's total limit), `sasl_reauth_refused()` returning 1, services `D F` (m_sasl.c), IAuth `f` (`iauth_sasl_end_failed(..., 1)`). An exchange whose request went out (`SASLX_SENT` in `con_sasl_xflags`: the local tier's `sasl_continue()` dispatch, the relayed `C` data to services, IAuth's data) and that the client ends without a login is counted by `sasl_exchange_abandoned()`: an abort (906), registering mid-exchange (`auth_complete_sasl()`), a timeout on the client's turn (local: not `SASL_STATE_WAITING_KC`; services/IAuth: `SASLX_CLIENTTURN` after their challenge) -- a timeout with the request still at the backend is not counted (a slow Keycloak must not punish users). A refused token counts when the refusal is known (the error challenge). Once per exchange (`SASLX_COUNTED`). Not counted: an abort before anything went out, services `D A`, 908 (services `M`, IAuth `l`), Keycloak/introspection/IAuth/services unavailable, agent splits, refusals before an exchange (907, 462), the WEBIRC hold's overflow. The limit mark (`con_sasl_limited`) is final (a raised limit never revives the connection); registration's check closes only outside an exchange's hold (`AR_SASL_PENDING`). Under `refresh` five failed refreshes lock a connection out of refreshing; the guess rate under `any`/`same` (a refresh resets the count) is bounded only by fake lag.
- A login resets it (`sasl_login_apply()` step 6 for SASL; IAuth's Z). At the limit before registration `con_sasl_limited` is set and **registration's check closes the connection** (`check_auth_finished()` first thing: `exit_client(..., "Too many SASL failures")`) -- every end of an exchange already runs that check (`auth_sasl_done()`, `sasl_hold_release()`) or owes it to the event loop (a Keycloak answer), and every caller already returns its `CPTR_KILLED`, so no new return contract. At the new-exchange point in `m_authenticate()` (after `EndSASLExchange()`), count >= limit (a lowered value too): before registration with an auth request `exit_client()`; else 904 ": too many failed attempts on this connection", nothing reaches a backend, nothing else changes -- until reconnect.

## Caches & Cross-Server Coherence

- Auth caches: SipHash-2-4 negative/positive; webhook handler with deauth via `AC U`.
- **Webhook**: a single *inbound* HTTP listener (`sasl_webhook_init(const struct kc_webhook_config *)` on top of libkc's `kc_webhook` server, config assembled in `sasl_conf.c`) receiving Keycloak events (password change / delete / disable / logout). Configured by a `Webhook {}` block (`port`, `secret`, `vhost`, `path`, the four limits, `signaturewindow` 300, `legacysecret` no, `realm` = the Keycloak block's realm by default); the `WEBHOOK_PORT` / `WEBHOOK_SECRET` features still work but log a deprecation warning at every rehash (the bed's confs use them). One port, no URL list, no outbound delivery.
- **Webhook transport (2026-09-23, plan 3)**: the SPI signs every delivery, `X-Webhook-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>." + body)>`, and puts `realmName` in every payload. `ircd/kc/kc_webhook_sig.c` (pure, cmocka) verifies within the window and keeps a 256-slot ring of event ids; `kc_webhook.c` answers 401 for missing / malformed / stale / mismatch / replay and 403 for another realm at HTTP time, counts each cause and calls the ircd's `on_reject` callback. A payload without `realmName` (an older SPI) is accepted and counted. `legacysecret = yes` accepts the plain `X-Webhook-Secret` header alone (deploy window only: SPI first, then ircd). The ring holds the ids the listener accepted with their newest signature `t` (user decision 2026-09-24): a copy signed no later than that is a replay (401); a copy the SPI signed again later is its own retry of an event already queued (its 200 was lost), answered 200 and not acted on again (`Duplicates` under STATS); an id the queue could not take (503) is forgotten so the retry is new. The realm check runs before the ring, so a refused foreign event takes no slot. **Plan 4 (2026-09-24): every ircd receives every event directly** (the SPI URL list names them all); a receiver purges its own caches, deauths ONLY the sessions it owns (`bounce_deauth_classify` SKIPs remote clients: `remote_ok` 0), and sends one `CI <names|*> <kc_id|*> <event_id> <kind>` relay carrying every name it resolved; an ircd-side applied-events log (`webhook_eventlog.c`, `WEBHOOK_EVENTLOG_SIZE` 1024) dedupes direct deliveries and relays by the event id; at end of burst `sasl_webhook_link_catchup` sends a new peer the last `WEBHOOK_EVENTLOG_WINDOW` (86400 s) as `CI ... B` lines, a superseded disable as a purge. KILL switches must match network-wide; deploy the chain together (an old server deauths nobody on a relay). A rehash that changes only the secret goes through `kc_webhook_set_secret` and keeps the listener and every counter; anything else re-inits (the handler's counters survive, libkc's listener counters are zeroed). A listener start that fails (busy port, bad `vhost`) leaves the ircd without a listener: it says so to every oper, `STATS webhook` reports NOT RUNNING, and the next rehash retries even with unchanged values. Surfaces: `STATS webhook` (oper: listener, events, refusals by cause, last refusal, handler counters) and a `SNO_UNAUTH` notice once per cause per 60 s. A payload `username` is used only if it can travel the wire (`username_usable` in `webhook_subject.c`: at most 32 bytes, no space, colon, control or DEL); otherwise the id alone resolves the subject.
- **Account timestamp on the wire (user rulings 2026-09-24):** the `ts` in `AC R|M <account> <ts> <id>` and `+r account:ts:id` is X3's registration date, stamped by X3 when it authenticates a user itself; X3's check refuses a stamp that differs from the date it knows (restored to its pre-a52968b form in x3 `feature/keycloak-identity`; "can't retire it yet", legacy servers still authenticate through X3). The fork sends `0` there on every local Keycloak login (nefarious `fix/no-ircd-account-timestamp`): Keycloak's creation time is the directory's date, not X3's. The SASL relay path (m_sasl.c) still carries X3's own stamp. The Keycloak id is the identity: a different id under a bound name RESETS the X3 handle (Rubin's rule) and the replaced id is remembered so old sessions (bursts, alias attaches, the ircd's 5-min SASL cache) bind instead of resetting again.
- **OAUTHBEARER validation (2026-09-24):** local JWKS validation first (no credential); `kc_url_introspect` now builds `.../openid-connect/token/introspect` (the bare `/introspect` answered 405 with a JSON body libkc read as `active=false`, so the fallback had never worked; nefarious `fix/oauthbearer-introspection`); a `KC_FORBIDDEN` local verdict (not a JWT, bad signature, expired) answers ERR_SASLFAIL at once and is not introspected. Nothing revokes an accepted token before `exp` except the fallback; Rubin accepts tokens-valid-until-expiry, Keycloak policy owns lifespans.
- **CI token**: `CACHEINVAL` / `CI` — a fork-only P10 token for cross-server cache coherence, sent only to IRCv3-aware peers (`sendcmdto_serv_butone_v3`); legacy servers never see it and would silently ignore it. Handled by `ms_cacheinval()` in `sasl_webhook.c`. Full wire forms: the `p10-protocol` skill.
- **CI id form (2026-09-23, plan 2 of the webhook audit)**: `CI <username|*> [<kc_id>]`. The positive cache entries carry the compact Keycloak id since step 5, so a delete or admin reset -- which Keycloak names only by uuid -- purges by id (`sasl_cache_invalidate_id`) here and on every fork server; `*` = no name. Old receivers ignore the second parameter and find nothing under `*`. Sender: `cache_invalidate_subject()` in `sasl_webhook.c`.
- **Webhook subject by id**: `USER` admin events carry no username (delete, reset-password: only `resourcePath: users/<uuid>`; update: the changed fields, `enabled` among them when it changed). `include/webhook_subject.h` (pure, cmocka over real fixtures under `ircd/test/fixtures/webhook/`) turns an event into (kind, compact id, payload name); the handler deauths under every account name the id resolves to and matches clients by id when both sides carry one. `authDetails` is the acting admin, never the subject (the parser no longer reads its username). Bed e2e: testnet `tests/src/services/keycloak-webhook-e2e.test.ts` (real admin actions on a throwaway user).

Read-only LDAP federation short-term (no services-side / X3 changes); Keycloak as authority long-term.

## Operational Notes

- Keycloak is **not** slow — test timeouts are usually test infrastructure, not Keycloak latency (avg ~45ms; rare ~1s outlier). Use generous timeouts (10s+ for SASL flows) and `retry: 2` for KC-dependent tests.
- Keycloak `PUT /admin/realms/{realm}/users/{id}` requires the FULL user representation; omitted fields get cleared. GET → merge → PUT, and update the `kc_user_repr_cache` AFTER merging (not before). Strip `credentials` from cached reprs — including them in a PUT ADDS a credential rather than replacing, causing duplicate passwords.
- **Async race on concurrent user updates**: when two async ops update the same user (e.g. email + attribute), the second op can read a cache populated by the first op's GET before the first op's PUT lands — its merge is against stale state, and its PUT overwrites the first op's changes. Mitigation: update the cache **immediately after merging** your changes (so the next op sees the new state), not after the PUT returns.
- **Keycloak user id at login — take it from the ID token, not the access token.** On Keycloak 25+ an access token's `sub` comes from the `basic` client scope; the ircd's client is admin-capable (manages accounts, receives events) and may not carry it, so never read `sub` from the access token. Ask the password grant for `scope=openid` and read `sub` from the returned `id_token`: it is mandatory there and independent of client scopes (the `basic` `sub` mapper targets only the access token and introspection — confirmed on the bed 2026-09-23, Keycloak 26.4.7). The userinfo endpoint is the other non-admin source. General rule (user, 2026-09-23): the ircd relies on non-admin Keycloak paths whenever feasible.
- **Credential scoping (direction, 2026-09-23):** the ircd's login paths (PLAIN, OAUTHBEARER) need no Keycloak role; only EXTERNAL, SCRAM/ECDSA and /REGISTER use the admin API. The bed's service account holds `manage-users` only (narrowed 2026-09-23: testnet `scripts/setup-keycloak.sh` grants it and removes a `realm-admin` left by an earlier run; realm-admin is never required). Decided direction: certificate login becomes a certfp grant type in the SPI jar (Keycloak `OAuth2GrantTypeFactory`), libkc gets a login pair and an admin pair; SCRAM/ECDSA are undecided (SPI lookup endpoint or retire). The certfp grant and the credential split are deferred (user, 2026-09-24; not a go-live condition — testnet `.claude/para/areas/deferred-items.md`). Measured minimum roles: query-users (EXTERNAL only), view-users (SCRAM/ECDSA), manage-users (/REGISTER). Design: testnet `.claude/para/projects/keycloak-certfp-grant-and-credential-scoping-2026-09.md`. Do not add ircd paths that need `view-users`/`manage-users`.

## Secrets

`KEYCLOAK_CLIENT_SECRET` and `WEBHOOK_SECRET` are deployment secrets — never paste secret values into this skill, a committed config, or any tracked file. Use templating/externalization for any config that carries them.
